## Combined tasks: 2.0.3 DocumentVersion + 2.0.4 DocumentNode + 2.0.5 Node Navigation

> Target runtime: Java 21  
> Previous completed task: `2.0.2 Split KnowledgeStore`

# 1. Goal

This batch introduces the first real **Document-Native knowledge model** into ModelRAG without replacing the existing chunk retrieval path yet.

The target domain becomes:

```text
Dataset
  │
  └── Document                     logical document
        │
        ├── DocumentVersion        immutable content snapshot
        │     │
        │     └── DocumentNode     structural knowledge tree
        │           │
        │           └── NodeEdge   non-tree relation
        │
        └── activeVersionId
```

At the end of this batch, ModelRAG must be able to represent and navigate:

```text
Document
└── Version 1
    └── DOCUMENT
        ├── SECTION
        │   ├── PARAGRAPH
        │   ├── PARAGRAPH
        │   └── TABLE
        └── SECTION
            └── PARAGRAPH
```

and support bounded navigation:

```text
open node
parent
children
previous
next
ancestors
references
```

This batch deliberately does **not** switch retrieval from `Chunk` to `DocumentNode`.

That will happen later.

# 2. Critical semantic rule: content version != index version

The current repository already uses:

```text
kb_document.version
kb_document.active_index_version
```

for the current legacy chunk/index lifecycle.

These fields are **index versions**, not document-content versions.

Do not reuse them for `DocumentVersion`.

After this batch, the two concepts must coexist:

```text
Content lifecycle:

kb_document.active_version_id
        ↓
kb_document_version.version_no

Legacy index lifecycle:

kb_document.version
kb_document.active_index_version
        ↓
kb_chunk.version
```

Example:

```text
Document content version: 1

Re-index same content 4 times:

kb_document_version.version_no = 1

kb_document.version = 5
kb_document.active_index_version = 5
```

This is valid.

Never derive the initial `DocumentVersion.versionNo` from `kb_document.version`.

For existing documents backfilled by `V54`, content version must start at:

```text
version_no = 1
```

regardless of current index version.

# 7. Why source_hash belongs to DocumentVersion

The current logical `kb_document.file_hash` is still used by legacy duplicate protection.

Do NOT remove or change that behavior in this batch.

However, future content revisions need a version-specific source hash.

Therefore `kb_document_version` should also carry:

```text
source_hash
```

Backfill it from:

```text
kb_document.file_hash
```

The legacy `kb_document.file_hash` and its V53 unique index remain unchanged for now.

Do NOT redesign duplicate-document policy in this batch.


# 16. Initial-version application transaction

Production document upload must not create `kb_document` without also creating and activating its initial `kb_document_version`.

Add a narrow application/domain service.

Recommended name:

```text
DocumentLifecycleService
```

Responsibilities:

```text
DatasetRepository
DocumentRepository
DocumentVersionRepository
TransactionOperations
```

Transaction:

```text
BEGIN

DatasetRepository.findById(datasetId)

DocumentRepository.create(...)
        ↓
logical Document

DocumentVersionRepository.create(...)
        ↓
version_no = 1

DocumentRepository.activateVersion(documentId, versionId)

DatasetRepository.bumpRevision(datasetId)

COMMIT
```

Return the refreshed logical document with `activeVersionId` set.

Keep this transaction short.

No parser, object storage, embedding, ES, or LLM calls may occur inside it.
