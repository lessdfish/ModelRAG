# ModelRAG 2.0 Task 2.0.1 - Remove Full-Dataset Retrieval From Hot Path

## 1. Goal

Fix the current retrieval context-expansion P0.

The online retrieval path must no longer load all chunks belonging to a dataset into JVM memory in order to expand parent/neighbor context.

This task is intentionally narrow.

Do not start DocumentNode, RetrievalUnit, Agent Runtime, or Python work.

---

## 2. Context

Current retrieval behavior approximately contains this anti-pattern:

```text
TopK candidates
↓
load all chunks in dataset
↓
build JVM map
↓
find parent / neighbors
↓
expanded context
```

This causes query-side work to scale with total dataset size.

At large scale:

```text
N = total chunks in dataset
K = selected top candidates
```

Current behavior trends toward:

```text
DB transfer: O(N)
JVM memory:  O(N)
map build:   O(N)
```

The target behavior is:

```text
TopK candidates
↓
bounded chunk lookup
↓
bounded parent lookup
↓
bounded neighbor lookup
↓
expanded context
```

Query work should become proportional to selected candidates and expansion radius.

## 4. Required Change

Remove any retrieval hot-path dependency on an API equivalent to:

```text
chunks(datasetId)
```

when it loads every active chunk for the dataset.

Introduce bounded legacy repository operations as needed.

Recommended operations:

```text
findChunksByIds(Collection<Long> ids)

findChunksByParentIds(Collection<Long> parentIds)

findChunkNeighbors(
    long documentId,
    int fromIndex,
    int toIndex
)
```

The exact names may be adjusted to fit the existing style.

Prefer batch-oriented APIs over one SQL query per chunk where possible.

---

## 5. SQL Requirements

Queries must be index-backed and bounded.

Typical query shapes may include:

```sql
SELECT ...
FROM kb_chunk
WHERE id = ANY (?)
  AND delete_time IS NULL;
```

or equivalent JDBC-compatible batched form.

Parent lookup:

```sql
SELECT ...
FROM kb_chunk
WHERE parent_chunk_id IN (...)
  AND delete_time IS NULL;
```

Neighbor lookup should be constrained by document and chunk index range:

```sql
SELECT ...
FROM kb_chunk
WHERE document_id = ?
  AND chunk_index BETWEEN ? AND ?
  AND delete_time IS NULL
ORDER BY chunk_index;
```

When active-index/version filtering is required, preserve the existing active-index semantics.

Do not weaken existing document deletion or active-version filters.

## 9. Batch Query Preference

Avoid N+1 queries.

Bad:

```text
TopK = 10

for each candidate:
    SELECT parent
    SELECT neighbors
```

Potential:

```text
20+ SQL queries
```

Prefer collecting:

```text
candidateIds
parentIds
document/index ranges
```

then issuing a small number of bounded batch queries.

If batching neighbor ranges cleanly is too complex for this task, correctness comes first, but report any N+1 risk explicitly.

---

## 10. Deduplication

Expanded context may include the same chunk through multiple paths.

Ensure final expanded context remains deduplicated.

Preserve the current ordering semantics if they are externally observable.

If the current code uses insertion-order deduplication, keep equivalent behavior.

---

## 11. Version / Active Index Semantics

The current retrieval path filters by active index/version.

Do not accidentally retrieve chunks from inactive index versions.

All new bounded lookup methods must preserve the same effective visibility rules as the previous full-dataset method.

Verify:

```text
document not deleted
chunk not deleted
correct active index version
```

when applicable.

---

## 12. Tests

Add/update tests proving:

### 12.1 Correct Parent Expansion

Given a selected chunk with `parent_chunk_id`, parent context is returned as expected.

### 12.2 Correct Neighbor Expansion

Given a selected chunk and configured radius, expected neighbor chunks are returned.

### 12.3 Deduplication

The same chunk selected through candidate/parent/neighbor paths appears only once in final context.

### 12.4 Active Version Filtering

Inactive-version chunks are not returned.

### 12.5 No Full-Dataset API Dependency

The retrieval expansion path must not require `chunks(datasetId)`.

Prefer a unit test with a fake/mock store that fails if the full-dataset method is invoked.

Example concept:

```java
@Override
public List<Chunk> chunks(long datasetId) {
    throw new AssertionError("full dataset load must not be used");
}
```

Then verify expansion still succeeds through bounded methods.

### 12.6 Existing Retrieval Compatibility

Existing retrieval tests should remain green.

## 14. Performance Acceptance

For a logical target of:

```text
1,000,000 chunks
TopK = 5
neighbor radius = 2
```

context expansion must not perform a full-dataset SELECT.

Expected rows fetched for context expansion should be on the order of:

```text
tens of rows
```

not:

```text
hundreds of thousands / millions
```

A practical acceptance target is:

```text
< 50 returned chunk rows
```

for typical Top5 + small-radius expansion, excluding the original recall channels.

---

## 15. Architecture Acceptance

After this task:

```text
Retrieval cost
```

must no longer depend linearly on:

```text
total dataset chunk count
```

for context expansion.

This task establishes the ModelRAG 2.0 invariant:

> No online retrieval hot path may load an entire dataset into JVM memory.

---

Task 2.0.1 is complete only when:

- retrieval context expansion no longer requires full-dataset chunk loading;
- bounded lookup APIs exist;
- bounded SQL is implemented;
- existing active-version behavior is preserved;
- tests cover parent/neighbor/dedup/version behavior;
- tests prove the old full-dataset path is not used;
- affected modules compile;
- relevant tests pass;
- no unrelated ModelRAG 2.0 phase has been started.
