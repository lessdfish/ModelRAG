# 一、修复 Active Build Overflow 时 V2 Lexical 被关闭

当前当 dataset 的 active build 数量超过 `modelrag.retrieval.v2.max-active-build-filter=10000` 时，`ActiveBuildScopeResolver` 会返回 `overflow=true`，随后 `HybridRetrievalService` 直接令 lexical channel 返回空列表。

这意味着 10001+ active builds 时：

```text
Hybrid Retrieval
    = Semantic Retrieval
      + 空的 Lexical Retrieval
```

百万规模 benchmark 恰好会触发这个路径，因此必须在 G11.1 修复。

保留小规模快速路径：

```text
activeBuildCount <= maxActiveBuildFilter
        ↓
PostgreSQL 获取 active build ids
        ↓
Elasticsearch terms filter
```

新增大规模 overflow 路径：

```text
activeBuildCount > maxActiveBuildFilter
        ↓
Elasticsearch bounded recall
        ↓
有限 Candidate
        ↓
PostgreSQL 批量 active validation
        ↓
过滤 stale candidate
        ↓
不足 topK 时 search_after / 下一页
        ↓
直到 topK 足够或达到安全上限
```

批量校验至少满足：

```sql
ru.dataset_id = ?
AND ru.id IN (...)
AND d.id = ru.document_id
AND d.active_index_build_id = ru.index_build_id
AND d.active_version_id = ru.document_version_id
```

必要时同时验证 document 未删除、dataset 未删除、index build state = ACTIVE。

禁止通过简单把 `10000` 改成 `100000` 来绕过问题。

# 二、补齐真实 Benchmark Loader

当前 benchmark manifest 可以声明：

```text

20,001 documents
10,001 active builds

```

但 runner 目前不能证明 PostgreSQL 和 Elasticsearch 中真实存在对应规模的数据。

必须形成完整链路：

```text
fixture generator
        ↓
benchmark loader
        ↓
PostgreSQL + pgvector
Elasticsearch
        ↓

        ↓
benchmark runner
        ↓
真实 report
```

建议新增：

```text

├── load_postgres.py
├── load_elasticsearch.py
└── load_all.py
```

也可以使用统一 loader，但要求：streaming、batch insert、bounded memory、deterministic、支持 smoke/full。

禁止一次性把 `1M × 1024` 向量全部载入 JVM/Python 内存。

Full 模式必须真实拥有：

```text
>= 20,000 active documents
>= 1,000,000 ACTIVE retrieval units
1024-d vectors
> 10,000 active index builds
stale/superseded units
shared V2 Elasticsearch index
```

# 五、Evaluation 改成 Single Execution

当前 V1 Evaluation：

```text
search.inspect()
    ↓
得到 retrieval result

qa.answer()
    ↓
内部再次 retrieval
```

当前 V2 也存在同样问题：

```text
retrieval.inspect()
    ↓
得到 candidates

qaV2.answer()
    ↓
内部再次 retrieval
```

于是：

```text
被评估的 Retrieval
!=
真正生成 Answer 使用的 Retrieval
```

本轮必须改成：

```text
一次 QA execution
   ↓
一次 Retrieval
   ↓
同一次 Evidence
   ↓
同一次 Answer
   ↓
一个 EvaluationObservation
```

建议新增内部对象：

```java
public record QaExecutionSnapshot(
    QaResult result,
    RetrievalExecutionSnapshot retrieval,
    EvidenceSet evidenceSet,
    long latencyMs,
    List<String> degradedComponents
) {}
```

具体名称可以调整，但生产 `answer()` 仍可只返回 `QaResult`，Evaluation 必须能拿到同一次执行产生的 retrieval/evidence/answer/refusal/latency。

禁止 Eval Adapter 再使用“先 search，再 qa”的方式。

# 七、修复 Missing Label Denominator

不同 metric 必须只统计真正有对应 label 的 case。

```text
Document Recall / MRR / nDCG
→ 只统计 expectedDocumentIds 非空的 case

Node Recall
→ 只统计 expectedNodeIds 非空的 case

Complete Evidence Recall
→ 只统计 expectedEvidenceGroups 非空的 case

Answer Accuracy
→ 只统计 expectedAnswer 非空的 case

Refusal metrics
→ 根据 shouldRefuse 统计
```

禁止：

```text
missing label = 0 score
```

报告中建议增加：

```text
eligibleCaseCount
totalCaseCount
coverage
status
```

# 八、Evidence Identity 必须 tuple 化

当前 `EvaluationObservation` 使用：

```text
documentIds[]
nodeIds[]
retrievalUnitIds[]
```

三个独立集合，这会产生跨 evidence 假命中。

新增：

```java
public record ObservedEvidenceIdentity(
    long documentId,
    Long documentVersionId,
    Long nodeId,
    Long retrievalUnitId,
    int rank,
    boolean selected
) {}
```

`EvaluationObservation` 增加真实 evidence tuple 列表。

Complete Evidence Recall 必须基于真实 tuple 判断，而不是分别对 document/node/unit 做集合交集。

必须新增回归测试：

```text
实际：
(doc10,node100,unit1000)
(doc20,node200,unit2000)

Gold：
(doc10,node200,unit1000)

结果必须 NOT MATCH
```

# 十二、修复 ERROR 与 REFUSED 语义

业务证据不足：

```text
status=REFUSED
refused=true
```

技术异常：

```text
status=ERROR
refused=false 或 NULL
```

如果当前 schema 不允许 null，则技术异常写 false。

禁止把数据库故障、ES 超时、RuntimeException 计为业务拒答。
