## Review result

G4 architecture is directionally correct: `IndexingPipeline` is now a V1/V2 facade, legacy indexing was extracted, real `DocumentNode -> RetrievalUnit -> IndexBuild` data is produced, V2 vector persistence is separate from legacy `PostgresVectorStore`, and V60 introduces a dedicated V2 lexical projection outbox.

However, G4 is not ready to pass the gate to G5 yet. Fix the four blocking items below.

## Blocker 1 - IndexBuildCompletionWorker race

Current flow allows two application replicas to read the same `LEXICAL_SYNCING` build.

Possible race:

```text
worker A reads LEXICAL_SYNCING
worker B reads LEXICAL_SYNCING

A: LEXICAL_SYNCING -> VERIFYING succeeds
B: same CAS loses -> lifecycle.transition throws
B: catch -> fail(buildId)
B: current state is VERIFYING -> build becomes FAILED
```

CAS contention must mean “another worker owns the build”, not “the build failed”.

Add a non-throwing ownership transition, preferably in `IndexBuildLifecycleService`:

```java
boolean tryTransition(
        long buildId,
        IndexBuildState expected,
        IndexBuildState next);
```

Then the completion worker should do:

```java
if (!lifecycle.tryTransition(
        build.id(),
        IndexBuildState.LEXICAL_SYNCING,
        IndexBuildState.VERIFYING)) {
    return;
}
```

Only the winner continues verification/activation. A failed CAS must never call `fail()`.

Add a two-worker/concurrency test proving that contention cannot mark a healthy build FAILED.

## Blocker 2 - StructurePersistStage concurrency

Current structure persistence checks `findRootByVersion()` and then inserts the tree, but it does not lock the immutable content version first.

Two workers can both observe no root. The loser can hit the unique-root constraint. In PostgreSQL, after a constraint violation the transaction is aborted; catching a translated exception inside the same transaction and trying to query the root again is not a reliable recovery strategy.

Add to `DocumentVersionRepository` / `JdbcDocumentVersionRepository`:

```java
void lockForStructure(long documentVersionId);
```

PostgreSQL:

```sql
SELECT id
FROM kb_document_version
WHERE id = ?
FOR UPDATE;
```

`StructurePersistStage` transaction must become:

```text
BEGIN
lock DocumentVersion
recheck findRootByVersion
if root exists -> reuse
else -> persist nodes and edges
COMMIT
```

Parsing must remain outside the transaction.

Add a two-thread test for the same `DocumentVersion`:

```text
both calls succeed
one reused=false
one reused=true
database has exactly one root/tree
```

## Blocker 3 - logical filename is lost

`DocumentParseStage` materializes the source to a random path like:

```text
modelrag-structured-123456.bin
```

while structured parsers may use `source.getFileName()` as the DOCUMENT root title.

That can leak the random temporary filename into:

```text
DocumentNode.title
RetrievalUnit.titlePath
embedding text
future citations
```

Change the structured parser API so the logical filename is explicit. For example:

```java
ParsedDocument parse(
        Path source,
        String logicalFileName,
        ParseLimits limits) throws Exception;
```

or use a small immutable `StructuredParseRequest`.

`DocumentParseStage` must pass:

```java
document.fileName()
```

The parser must never use the random temp path as user-visible document identity.

Add MD/TXT/DOCX/PDF tests verifying the root/titlePath does not contain:

```text
modelrag-structured-
```

## Blocker 4 - LexicalProjectionStage must not be optional

`IndexBuildCoordinator` currently uses `ObjectProvider<LexicalProjectionStage>`.

If the stage is absent, the build can remain silently stuck in:

```text
VECTOR_READY
```

For the current G4 build profile, lexical projection is required before READY.

Prefer direct constructor injection:

```java
private final LexicalProjectionStage lexical;
```

Provide a test `RetrievalProjectionOutbox` fake under the test profile so the stage can be wired in tests.

Missing production wiring should fail startup instead of creating a permanently stuck build.
