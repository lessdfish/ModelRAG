# ModelRAG 2.0 — G11.5 Retrieval Performance Diagnosis（检索性能拆解与定位）

## 基线 Commit
`f5eb958eaeebfe5d1c1fd994621a7069411a7684`

> 如果 G11.4 已产生新提交，Codex 开始执行前必须先读取 `git rev-parse HEAD`，并把实际 HEAD 作为本轮基线写入最终报告。不要 checkout、reset 或覆盖用户已有修改。

## 本轮目标

第一次真实 Smoke 已证明 Retrieval Correctness（检索正确性）基本闭合，但当前 Smoke 下仍有较高 `degradedRate` 和真实 `timeoutRate`。本轮不要继续“猜瓶颈”，而是把真实耗时拆出来，回答：

```text
800ms 到底花在哪里？
```

Semantic Channel 需要拆成：

```text
queue wait
+ embedding cache
+ remote embedding call
+ pgvector search
+ mapping / validation
```

Lexical Channel 需要拆成：

```text
queue wait
+ Elasticsearch request
+ active validation
+ lexical-query internal fusion
```

核心原则：

```text
Measure first
Optimize second
Tune timeout last
```

## 二、P0：Semantic Channel 延迟拆分

至少得到：

```text
semantic.queueWaitMs
semantic.embeddingTotalMs
semantic.embeddingRemoteMs
semantic.vectorSearchMs
semantic.totalMs
```

如果当前架构存在独立 Embedding Cache，再记录：

```text
semantic.embeddingCacheLookupMs
semantic.embeddingCacheHit
```

如果不存在，则明确：

```text
embeddingCache = NOT_PRESENT
```

不要为了统计强行新增缓存。

所有 timing 必须来自真实 `System.nanoTime()` 或 Micrometer，禁止估算。

## 三、P0：测 Queue Wait

提交异步任务前记录：

```java
long submittedAt = System.nanoTime();
```

任务真正开始时记录：

```java
long startedAt = System.nanoTime();
```

得到：

```text
semanticQueueWaitMs
lexicalQueueWaitMs
rerankQueueWaitMs（如参与）
```

不要把 queue wait 混入 Embedding / ES / DB 延迟。

## 四、P0：Embedding 延迟继续细分

当前路径：

```text
HybridRetrievalService
→ TextEmbeddingProvider
→ RemoteEmbeddingProvider
→ AiServiceClient
→ /v1/embeddings
→ 临时 Bridge
→ Ollama /api/embed
```

记录 Java 侧：

```text
remoteEmbeddingCallMs
```

如果需要增强临时 Bridge，只允许修改 `$env:TEMP` 下临时脚本，不提交到仓库。

Bridge 最好记录：

```text
bridge.totalMs
bridge.ollamaCallMs
requestCount
failureCount
```

最终必须标注：

```text
TEMP TOOL ONLY
```

同时执行：

```powershell
ollama version
ollama list
ollama ps
```

记录：
- `qwen3-embedding:0.6b`
- Processor 是 GPU / CPU / Mixed
- 模型是否常驻
- 是否可能频繁 reload

如果不是 GPU，只报告，不自动改用户系统设置。

## 五、P0：pgvector 单独计时

必须得到：

```text
vectorSearchMs
```

如果异常高，允许仅在 Benchmark DB 执行：

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
```

检查：
- HNSW 是否使用
- 是否 Seq Scan
- dataset filter
- active identity filter/join

不要对用户日常数据库做破坏性操作。

## 七、P1：区分 Timeout Plateau 和真实完成时延

Benchmark report 必须同时保留：

```text
requestLatencyMs
stageLatencyMs
timeoutComponent
```

对于被 800ms channel budget 截断的请求，明确标识：

```text
TIMED_OUT_AT_CHANNEL_BUDGET
```

不要把最终 HTTP latency 的 840~890ms 误解释为“真实 Semantic 完成时延”。

## 八、P1：检查缓存 / 双峰分布

Benchmark query 使用 `request_number % 20`，每 workload 的 100 次请求只有大约 20 个 unique query。

必须检查：
- 是否存在 embedding cache
- cache hit/miss
- warm/cold model effect

如果存在缓存，输出：

```text
embeddingCacheHitRate
```

如果不存在，输出：

```text
embeddingCache = NOT_PRESENT
```

不要为了 Benchmark 偷偷关闭缓存。

## 十二、允许的低风险优化

只有在证据明确时才允许实施小改动，例如：
- 模型频繁 reload：给出 keep-alive / resident 建议
- executor queue 明显过高：检查线程池/并发配置
- pgvector Seq Scan：检查已有 HNSW/SQL query
- ES active validation 占比高：优化批量验证

禁止：
- 无数据就调大 timeout
- 无数据就扩大线程池
- 无数据就改 HNSW 参数
- 无数据就新增缓存

若需要大结构改造，输出：

```text
PERFORMANCE ISSUE IDENTIFIED
```

并停止，等待下一轮设计。
