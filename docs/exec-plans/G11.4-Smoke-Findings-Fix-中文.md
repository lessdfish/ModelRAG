## 基线 Commit

`f5eb958eaeebfe5d1c1fd994621a7069411a7684`

## 本轮背景

第一次真实 Smoke Benchmark 已经完成：

```text
20,000 active RetrievalUnit
2,000 active Document
200 stale RetrievalUnit
PostgreSQL + pgvector
Elasticsearch
Java 21
Ollama qwen3-embedding:0.6b

```

```text
errorRate = 0

实测暴露出 4 类问题：

3. Benchmark Endpoint 把 timeout 固定返回 false，导致 `timeoutRate=0` 不可信。
4. `evidenceValid=false` 同时表示“没有候选”和“候选身份非法”，统计语义混乱。

本轮目标：

```

# 一、P0：Semantic Query 与 Lexical Query 分离

## 当前问题

当前 `QueryRewriter.expand()` 生成一组：

```text
searchQueries
```

内容可能包括：

```text
原始 Query
关键词抽取
中文二元组
意图扩展词
Latin token
同义词
```

随后 `HybridRetrievalService` 将同一组 `searchQueries` 同时用于：

```text
Semantic Search
Lexical Search
```

Semantic 当前实际执行：

```java
for (String query : queries) {
    float[] embedding = embeddings.embed(...);
    semantic.search(...);
}
```

因此一条用户问题可能触发最多 5 次 Query Embedding。

而整个 Semantic Channel 共用默认：

```text
modelrag.search.channel-timeout-ms = 800
```

真实 Smoke 中 Semantic 基本稳定撞到 800ms 左右，导致：

```text
semantic-only degraded = 100%
hybrid degraded = 100%
broad degraded = 100%
stale-build-exclusion degraded = 100%
```

## 目标设计

明确拆成两种查询：

```text
Semantic Query（语义查询）
= 1 个适合 Embedding 的自然语言查询

Lexical Queries（关键词查询）
= 多个适合 ES/BM25 的关键词、条款号、token、同义词查询
```

建议将：

```java
QueryExtensionResult
```

演进为类似：

```java
public record QueryExtensionResult(
    String originalQuery,
    String rewrittenQuery,
    String semanticQuery,
    List<String> lexicalQueries,
    String rerankQuery
) {}
```

### Semantic Query 推荐来源

优先使用：

```text
rewrittenQuery
```

要求：
- 去多余空白；
- 保留自然语言语义；
- 不加入 dense bigram；
- 不加入专门服务 BM25 的 token 串；
- 默认只做 1 次 embedding。

### Lexical Queries

继续允许：

```text
原始/规范化 query
keywords
denseTerms
intentTerms
latinTokens
synonymTerms
```

最多 5 条。

### Rerank Query

继续使用：

```text
rewrittenQuery / semanticQuery
```

不要使用 denseTerms/bigram 作为 rerank query。

# 二、不要简单扩大 800ms Timeout

本轮不允许直接：

```text
800ms -> 3000ms
```

作为主修复。

正确顺序：

```text
先把 Semantic Query 减少为 1 次 Embedding
↓
重新跑 Smoke
↓
再看真实 Semantic latency
↓
如果 800ms 仍明显不合理
再单独讨论 SLO / timeout 配置
```

如果最终仍需要调整 timeout：
- 必须有新 Smoke 数据证明；
- 必须记录调整前后 p95/p99；
- 不得仅为了 Gate 通过。

# 三、P0：Benchmark Timeout 必须真实透传

## 当前问题

当前 `RetrievalBenchmarkController` 返回：

```java
new Response(
    degraded,
    false, // timeout 被固定为 false
    ...
)
```

所以即使 Semantic 已经发生 channel timeout：

```text
timeoutRate 仍然 = 0
```

## 目标

Benchmark Endpoint 必须根据真实 `RetrievalV2Stages.degradedComponents()` 判断超时。

至少支持：

```text
SEMANTIC_TIMEOUT
SEMANTIC_ERROR
LEXICAL_TIMEOUT
LEXICAL_ERROR
RERANK_TIMEOUT
RERANK_ERROR
```

不要求一次做复杂异常体系，但 timeout 必须可识别。

Benchmark Controller：

```text
timeout = degradedComponents 中存在 *_TIMEOUT
```

普通 error：

```text
degraded=true
timeout=false
```

Runner 继续统计：

```text
timeoutRate
```

# 四、P0：Evidence Validation 状态拆分

## 当前问题

现在：

```java
if (candidates.isEmpty()) {
    return new ValidatedCandidates(List.of(), 0, false);
}
```

因此：

```text
没有 Candidate
```

和：

```text
返回了 Candidate，但 Candidate 身份错误
```

都会变成：

```text
evidenceValid=false
```

## 目标

至少拆成：

```text
NO_EVIDENCE
VALID
INVALID
```

推荐新增：

```java
enum EvidenceValidationStatus {
    NO_EVIDENCE,
    VALID,
    INVALID
}
```

Benchmark Response 增加：

```text
evidenceStatus
```

Runner 分别统计：

```text
noEvidenceCount
invalidEvidenceCount
```

不要再把空结果计入 invalid evidence。

# 五、P0：修正 Smoke Sentinel 的语义

## 当前问题

Smoke：

```text
2,000 active builds
```

而 active-build overflow cap：

```text
10,000
```

因此 Smoke 根本没有进入：

```text
>10,000 active build overflow path
```

当前却把：

```text
最终 TopK 没出现 sentinel
```

直接解释为：

```text
activeBuildTruncated=true
```

这在 Smoke 语义上不准确。

## 新语义

拆成两个不同指标：

### Smoke / 普通规模

```text
sentinelRecall
```

含义：Sentinel 是否能通过真实生产 Retrieval Pipeline 被召回。

### Full / >10k Active Build

```text
activeBuildTruncationStatus
```

只有在：

```text
manifest.activeBuildCount > activeBuildFilterLimit
```

时才允许计算。

否则：

```text
NOT_APPLICABLE
```

推荐：

```text
activeBuildTruncationStatus:
NOT_APPLICABLE
PASS
FAIL
```

# 六、P1：精确 Sentinel Query 不应被 Lexical 扩展结果挤出

第一次 Smoke 已证明：

```text
ES 精确查询 Sentinel -> 命中
PostgreSQL Active Validation -> 正确
应用最终 Candidate -> Sentinel 丢失
```

必须新增生产级回归测试：

```text
HybridRetrievalService.Mode.LEXICAL_ONLY
query = G11_ACTIVE_BUILD_SENTINEL_2000
最终 TopK 必须包含 Sentinel
```

## 重点排查

当前多 Query Lexical 流程可能出现：

```text
Query A raw ES score
Query B raw ES score
Query C raw ES score
```

直接合并比较。

不同 Query 的 ES `_score` 不能默认当成绝对同尺度。

如果确认问题来自跨 Query raw score 混排，优先改成：

```text
每个 lexical query 内部排名
↓
跨 query 使用 RRF（倒数排名融合）
↓
得到统一 Lexical Candidate 排名
```

不要破坏外层 Semantic + Lexical 的现有 Hybrid RRF。

如果测试证明 Sentinel 丢失与 raw score 无关，则不要强行引入 RRF，修真实根因。

# 八、必须新增的测试

1. Semantic Query 只 Embedding 一次：复杂 query 可以生成多个 lexicalQueries，但 semantic embedding invocation count == 1。
2. Lexical 仍保留多查询扩展能力。
3. Semantic timeout -> `SEMANTIC_TIMEOUT`，Benchmark `timeout=true`。
4. Semantic 普通异常 -> `SEMANTIC_ERROR`，Benchmark `timeout=false`。
5. `candidateCount=0 -> NO_EVIDENCE`。
6. Candidate 全部 active-valid -> `VALID`。
7. Candidate 身份/active 校验失败 -> `INVALID`。
8. Smoke 2,000 build -> `sentinelRecall=true` 且 `activeBuildTruncationStatus=NOT_APPLICABLE`。
9. Full >10k build -> 才测试 `activeBuildTruncationStatus=PASS/FAIL`。
10. `Mode.LEXICAL_ONLY` 精确 Sentinel 最终 TopK 必须包含 Sentinel。
