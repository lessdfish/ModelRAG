# ModelRAG 2.0 G5 - Retrieval V2
## Combined tasks: 2.0.11 Semantic Retrieval V2 + 2.0.12 Lexical Retrieval V2

> Target runtime: Java 21  
> Prerequisite: G4.1 stabilized and green  
> Current production read path: V1 Chunk retrieval  
> G5 strategy: build a complete RetrievalUnit-based V2 query path and run it in shadow mode; do not cut over QA yet  
> Flyway: no new migration required by default

---

# 1. Goal

G4 made V2 data real:

```text
source document
    ↓
DocumentVersion
    ↓
DocumentNode
    ↓
RetrievalUnit
    ├── kb_vector_embedding
    └── modelrag-retrieval-units-v2
    ↓
IndexBuild
    ↓
kb_document.active_index_build_id
```

But current online search still uses:

```text
Chunk
    ├── kb_chunk.embedding
    └── modelrag-chunks-active
    ↓
SearchOrchestrator
    ↓
ScoredChunk
```

G5 creates the first complete V2 retrieval path:

```text
Query
  ↓
QueryRewriter
  ↓
┌─────────────────────────────┐
│                             │
▼                             ▼
Semantic Retrieval V2        Lexical Retrieval V2
pgvector                       Elasticsearch
kb_vector_embedding            modelrag-retrieval-units-v2
│                             │
└──────────────┬──────────────┘
               ▼
       RetrievalCandidate
               ↓
              RRF
               ↓
       optional Reranker
               ↓
        RetrievalV2Stages
```

The key migration rule is:

> G5 creates a queryable V2 retrieval engine, but V1 remains the user-facing production result.

V2 is executed only through an explicit V2 facade or optional shadow comparison.

Do not switch `QaOrchestrator` / `RetrievalPipeline` to V2 in this batch.

# 8. Why unit ID is the fusion key

One `RetrievalUnit` has:

```text
one semantic representation
+
one lexical projection
```

Therefore semantic and lexical hits for the same unit should fuse on:

```text
retrievalUnitId
```

RRF must not fuse by:

```text
nodeId
documentId
content hash
```

because one node can legitimately produce multiple windows/units.

Later Evidence selection may collapse related units.

Not in G5.

# 13. Semantic active-build SQL

The semantic query must enforce active V2 visibility inside PostgreSQL.

Required logical SQL:

```sql
SELECT
    u.id AS retrieval_unit_id,
    u.dataset_id,
    u.node_id,
    u.document_id,
    u.document_version_id,
    u.index_build_id,
    u.unit_type,
    u.title_path,
    u.content,
    u.metadata,
    1 - (e.embedding <=> CAST(? AS vector)) AS score
FROM kb_vector_embedding e
JOIN kb_retrieval_unit u
  ON u.id = e.retrieval_unit_id
 AND u.index_build_id = e.index_build_id
JOIN kb_document d
  ON d.id = u.document_id
JOIN kb_dataset ds
  ON ds.id = u.dataset_id
JOIN kb_index_build b
  ON b.id = u.index_build_id
WHERE u.dataset_id = ?
  AND e.embedding_profile = ?
  AND d.delete_time IS NULL
  AND ds.delete_time IS NULL
  AND d.active_version_id = u.document_version_id
  AND d.active_index_build_id = u.index_build_id
  AND b.state = 'ACTIVE'
ORDER BY e.embedding <=> CAST(? AS vector)
LIMIT ?
```

The exact selected columns may differ.

Hard invariants:

```text
activeVersionId matches unit version
activeIndexBuildId matches unit build
build state is ACTIVE
embedding profile matches
soft-deleted document/dataset excluded
```

No stale build may be returned.

# 20. Lexical active-build correctness problem

The G4 V2 ES index intentionally contains historical builds:

```text
Build 1 units
Build 2 units
Build 3 units
...
```

A query filtered only by:

```text
datasetId
```

is incorrect because stale builds may be returned.

G5 must never return a stale build as a V2 lexical candidate.

Elasticsearch cannot directly join:

```text
kb_document.active_index_build_id
```

from PostgreSQL.

Therefore G5 needs an explicit active-build scope.

---

# 21. ActiveBuildScopeResolver

Add:

```text
ActiveBuildScopeResolver

```

Recommended `ActiveBuildRef`:

```text

```

Extend `IndexBuildRepository` with a bounded query such as:

```java

        long datasetId,
        int limit);
```

Production SQL should derive truth from both:

```text
kb_document.active_index_build_id
+
kb_index_build.state='ACTIVE'
```

and active content version.

Example:

```sql
SELECT
    d.id AS document_id,
    d.active_version_id AS document_version_id,
    d.active_index_build_id AS index_build_id,
    b.embedding_profile
FROM kb_document d
JOIN kb_dataset ds
  ON ds.id=d.dataset_id
JOIN kb_index_build b
  ON b.id=d.active_index_build_id
 AND b.document_id=d.id
WHERE d.dataset_id=?
  AND d.delete_time IS NULL
  AND ds.delete_time IS NULL
  AND d.active_version_id=b.document_version_id
  AND b.state='ACTIVE'
ORDER BY d.id
LIMIT ?
```

# 22. Active-build scope must be bounded

Do not introduce:

```text
load every active build in an arbitrarily huge dataset forever
```

Configure:

```text
modelrag.retrieval.v2.max-active-build-filter
```

Recommended initial default:

```text
10000
```

Resolve with:

```text
limit = cap + 1
```

If more than cap active builds exist:

```text
do not query ES with a silently truncated filter
```

Instead:

```text
mark lexical V2 degraded
return empty lexical V2 channel
continue semantic V2
```

Correct degradation is better than stale/incorrect lexical evidence.

This cap is acceptable for G5 because V2 remains shadow-only.

Before V2 production cutover, large-dataset lexical activation/routing must be validated under load.

# 26. Defense-in-depth active validation

Even though the ES query contains active build IDs, after lexical hits return, validate candidate unit IDs in one bounded batch through:

```text
RetrievalUnitRepository.findActiveByIds(datasetId, ids)
```

Then retain only candidates whose:

```text
retrievalUnitId
documentVersionId
indexBuildId
```

match the active PostgreSQL row.

Reason:

```text
ES is an eventually consistent projection.
PostgreSQL is source of truth.
```

This is a bounded Top-N validation, not a full dataset read.

If ES returns 40 candidates:

```text
one bounded DB validation query
```

is acceptable.

Do not issue one DB query per hit.

# 31. Degraded behavior

Required:

```text
semantic down
→ lexical continues

lexical/ES down
→ semantic continues

active-build lexical scope > configured cap
→ semantic continues, lexical marked degraded

reranker down
→ fused RRF continues

both semantic and lexical down/empty
→ return empty V2 candidates
```

Do not throw V2 shadow failures into the V1 user request.

# 33. Candidate deduplication

Within one channel, multiple rewritten queries may return the same unit.

Deduplicate by:

```text
retrievalUnitId
```

Keep the best native score/rank representative.

Do not dedupe by identical content.

Two different units may intentionally contain overlapping text.

```text
modelrag.retrieval.v2.shadow-enabled=false
```

V2 is not called.

### SH2. enabled

V1 result returns normally and V2 comparison executes asynchronously.

### SH3. V2 failure

V1 result is unchanged.

### SH4. bounded queue/executor

Shadow load cannot create an unbounded queue.

### SH5. document overlap

Comparison uses document IDs, not chunk/unit IDs.
