# ModelRAG 2.0 G8 — Durable Agent Runtime

## 2.0.19 AgentState + 2.0.20 AgentRuntime + 2.0.21 Checkpoint / Resume

> Target runtime: Java 21  
> Base commit reviewed: `e73fde4121dbef373b444fbf1aa6fd4b94ba6c7d`  
> Prerequisite: G7.1 accepted  
> Scope: make non-direct Agent execution explicit, durable, single-owner and resumable  
> Flyway: add **V64 only**; keep V61-V63 reserved by the architecture plan  
> Do not start G9 / Tool Gateway extraction

---

# 1. Goal

After G7.1, ModelRAG has a real Agentic Retrieval loop:

```text
Goal
→ LlmAgentPolicy
→ Retrieval Action
→ RetrievalObservation
→ Evidence
→ repeat / FINISH
→ one AnswerSynthesizer call
```

and a separate TOOL_AGENT path with approval, authorization, idempotency and HTTP-tool safeguards.

The remaining architectural weakness is state ownership.

Today important Agent state still lives in process-local variables:

```text
List<RetrievalObservation>
List<Evidence>
observedNodeIds
observedDocumentIds
remaining budgets

TOOL_AGENT observations
action fingerprints
current subtask
approval continuation context
```

If the JVM dies, another replica cannot safely continue that exact execution.

G8 changes the mental model to:

```text
Agent execution
    ↓
AgentState
    ↓
PostgreSQL checkpoint
    ↓
lease / single-writer ownership
    ↓
AgentRuntime
    ↓
one bounded state transition
    ↓
checkpoint
    ↓
next transition
```

Hard invariant:

> PostgreSQL owns durable Agent state. Java thread maps only own ephemeral cancellation handles.

Do not regress these guarantees.

# 18. Critical fix: registration must not reset an existing execution

Current `AgentExecutionRegistry.register()` uses:

```sql
INSERT ...
ON CONFLICT(execution_id)
DO UPDATE ... status='RUNNING'
```

This is unacceptable once checkpoints exist.

A duplicated/retried execution ID must never reset:

```text
WAITING_APPROVAL
CANCELLED
DONE
checkpoint sequence
lease
```

Target:

```text
createNewExecution(...)
```

is insert-only.

On duplicate:

```text
verify existing scope
return existing execution or reject conflict
```

but never overwrite durable state.

Keep a separate explicit resume path.

# 19. Checkpoint atomicity

One checkpoint write must atomically update:

```text
kb_agent_execution summary/pointers
+
kb_agent_checkpoint row
```

Use the existing transaction infrastructure.

Recommended optimistic rule:

```text
expectedSeq = state.checkpointSeq
nextSeq = expectedSeq + 1
```

Inside one transaction:

```sql
UPDATE kb_agent_execution
SET
    status=?,
    current_step=?,
    budget_json=?,
    result_json=?,
    last_checkpoint_seq=?,
    state_version=?,
    ...
WHERE execution_id=?
  AND last_checkpoint_seq=?
  AND lease_owner=?;
```

Require:

```text
updated rows == 1
```

Then insert:

```text
checkpoint_seq = nextSeq
```

If any part fails:

```text
rollback all
```

No half-checkpoint.

---

# 20. Why optimistic sequence is required

Without checkpoint CAS:

```text
replica A loads seq 4
replica B loads seq 4

A writes seq 5
B writes seq 6 from stale state
```

The second write can overwrite logical progress.

With:

```text
WHERE last_checkpoint_seq = expectedSeq
```

only one writer wins.

The loser must stop and reload; it must not continue executing actions.

# 21. Lease ownership

Add PostgreSQL-backed single-writer lease.

Recommended config:

```text
modelrag.agent.runtime.lease-seconds=30
modelrag.agent.runtime.recovery-poll-ms=5000
modelrag.agent.runtime.recovery-batch-size=20
```

Each JVM instance has a stable runtime owner ID, for example:

```text
hostname/process UUID
```

Claim rule:

```sql
UPDATE kb_agent_execution
SET lease_owner=?, lease_until=NOW() + ...
WHERE execution_id=?
  AND status='RUNNING'
  AND (
      lease_until IS NULL
      OR lease_until < NOW()
      OR lease_owner=?
  );
```

Only one replica may own an execution.

# 33. Business-tool idempotency key

For idempotent HTTP tools:

```text
Idempotency-Key
```

must be derived from the persisted action ID and remain identical on resume.

Example:

```text

```

```text

```

This is the only safe automatic replay model.

If a process restarts and checkpoint shows:


```text

```

# 43. Deadline

Persist absolute:

```text

```

Example:


# 52. Failure boundaries

### checkpoint write fails before action

```text
do not execute action
```

### read-only action succeeds, outcome checkpoint fails

```text
resume may replay same persisted pending action
```

### idempotent HTTP action succeeds, outcome checkpoint fails

```text
resume may replay same action ID / idempotency key
```

### non-idempotent side effect outcome unknown

```text
RECONCILIATION_REQUIRED
```

### final synthesis succeeds, terminal checkpoint fails

This is tricky.

Use a persisted pending FINAL_SYNTHESIS action or equivalent terminal write-ahead state so a restart does not blindly generate another answer without knowing the previous call happened.

Since final answer generation is side-effect-free from the business perspective, a retry is acceptable if necessary, but metrics/token cost may duplicate.

Prefer persisting:

```text
pendingAction = FINAL_SYNTHESIS
```

before the model call.

If the model call result is lost before checkpoint, resume may regenerate once under the same state.

Do not claim exactly-once model billing.
