# ModelRAG 2.0 — G11.6 ANN-First Semantic Retrieval + Real Timeout Cancellation

PostgreSQL EXPLAIN 已证明，当前生产等价 Semantic SQL 会先进行多表 Join 和 Active Version/Build 校验，再执行距离排序与 LIMIT，导致 HNSW 没有稳定成为真正的 ANN Top-K 主路径。

本轮目标：

> 将 V2 Semantic Retrieval 从“先全量关系过滤，再向量排序”改成“ANN-first（向量近邻优先召回）→ Active Identity Validation（有效身份校验）→ bounded refill（有界补召回）”，同时让数据库查询在 Channel Deadline 到来前真正停止，避免 Future 已 timeout 但 JDBC/SQL 仍继续占用 semantic executor。

## 3. P0：把 Semantic SQL 改为 ANN-First

### 当前问题

现有 `PostgresSemanticSearchAdapter` SQL 形态类似：

```sql
FROM kb_vector_embedding e
JOIN kb_retrieval_unit u ...
JOIN kb_document d ...
JOIN kb_dataset ds ...
JOIN kb_index_build b ...
WHERE active version/build ...
ORDER BY e.embedding <=> ?
LIMIT ?
```

这使 Planner 很容易先处理 Join / Active 条件，再对大量行计算距离并排序。

### 新执行模型

```text
Query Embedding
      ↓
ANN Candidate Recall
只访问 kb_vector_embedding 的向量投影
      ↓
有限候选，例如 80/160/320...
      ↓
Active Identity Validation + RetrievalUnit Hydration
      ↓
如果有效候选不足 TopK
      ↓
bounded refill
      ↓
最终 TopK Semantic Candidate
```

关键：

> ANN 子查询必须在关系 Join 之前完成 Top-N 截断。

## 4. 推荐 SQL 形态：MATERIALIZED ANN Candidate CTE

优先尝试：

```sql
WITH ann AS MATERIALIZED (
    SELECT
        e.retrieval_unit_id,
        e.dataset_id,
        e.document_id,
        e.document_version_id,
        e.index_build_id,
        e.embedding <=> CAST(? AS vector) AS distance
    FROM kb_vector_embedding e
    WHERE e.dataset_id = ?
      AND e.embedding_profile = ?
    ORDER BY e.embedding <=> CAST(? AS vector)
    LIMIT ?
)
SELECT
    u.id AS retrieval_unit_id,
    u.dataset_id,
    u.node_id,
    u.document_id,
    u.document_version_id,
    u.index_build_id,
    u.unit_type,
    u.title_path,
    u.content,
    u.metadata,
    1 - ann.distance AS score
FROM ann
JOIN kb_retrieval_unit u
  ON u.id = ann.retrieval_unit_id
 AND u.dataset_id = ann.dataset_id
 AND u.document_id = ann.document_id
 AND u.document_version_id = ann.document_version_id
 AND u.index_build_id = ann.index_build_id
JOIN kb_document d ON d.id = u.document_id
JOIN kb_dataset ds ON ds.id = u.dataset_id
JOIN kb_index_build b ON b.id = u.index_build_id
WHERE d.delete_time IS NULL
  AND ds.delete_time IS NULL
  AND d.active_version_id = u.document_version_id
  AND d.active_index_build_id = u.index_build_id
  AND b.state = 'ACTIVE'
ORDER BY ann.distance
LIMIT ?
```

`MATERIALIZED` 的目标是强制：

```text
先 ANN LIMIT
再 Join
```

避免 Planner 内联后又退回“先 Join 再全量距离排序”。

Codex 必须用真实：

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
```

确认真正执行计划。如果另一种等价 SQL 计划更好，可以采用，但必须在最终报告解释。

## 5. ANN Candidate Budget 与 bounded refill

不能简单：

```text
ANN LIMIT = final TopK
```

因为最邻近候选里可能有 stale build / old version / deleted document。

建议：

```text
final topK = request.limit

initial candidate count:
max(64, topK * 4)

不足：
candidate count × 2

例如：
80 → 160 → 320 → 640
```

必须有硬上限，例如：

```text
max ANN candidates <= 1000
max refill rounds <= 4
```

具体数值可按代码风格配置，但必须：

```text
有界
不会无限循环
不会全表 fallback
```

到上限仍不足 TopK：

```text
返回当前 active-valid candidates
```

并记录：

```text
SEMANTIC_ANN_REFILL_EXHAUSTED
```

可以 degraded，但不能泄漏 stale candidate。

## 6. 身份校验不得退化

最终 Candidate 必须继续验证：

```text
datasetId
retrievalUnitId
documentId
documentVersionId
indexBuildId
```

并满足：

```text
document.active_version_id == unit.document_version_id
document.active_index_build_id == unit.index_build_id
index_build.state == ACTIVE
dataset/document 未删除
```

不得因为 ANN-first 引入：

```text
旧 version
旧 build
stale vector
另一个 dataset
```

G11.4/G11.5 correctness 不得回归：

```text
noStaleBuildLeakage = true
boundedResults = true
validEvidence = true
sentinelRecall = true
invalidEvidenceCount = 0
```

## 7. P0：Database-Level Deadline / Cancellation

### 当前风险

当前上层使用：

```java
CompletableFuture.orTimeout(800ms)
```

只能让 Future 超时，不保证 blocking JDBC query 真正停止。

可能形成：

```text
800ms Future timeout
→ HTTP 降级返回
→ PostgreSQL SQL 仍跑 3~4s
→ semantic executor worker 长时间占用
→ queue wait
→ timeout cascade
```

### 目标

数据库 SQL 自身必须拥有 deadline。

优先使用 PostgreSQL：

```sql
SET LOCAL statement_timeout = '<remaining-budget-ms>ms'
```

当前 adapter 已使用 read-only transaction，可以在同一事务中：

```sql
SET LOCAL hnsw.iterative_scan = 'relaxed_order';
SET LOCAL statement_timeout = '...ms';
```

再执行 ANN query。

## 8. Deadline 使用“剩余预算”

Semantic Channel 800ms 包含：

```text
queue wait
+ embedding
+ vector search
```

所以 DB 不能固定再拿完整 800ms。

推荐从 `HybridRetrievalService` 向 `SemanticSearchRequest` 传入：

```text
queryTimeoutMs / remainingBudgetMs
```

计算：

```text
remainingMs =
channelDeadline - now - safetyMargin
```

例如：

```text
Channel = 800ms
queue = 20ms
embedding = 160ms
safety margin = 25ms

DB remaining ≈ 595ms
```

Safety Margin 可取 20~50ms，给：

```text
Row mapping
Candidate validation
Future completion
Controller response
```

如果剩余预算已经很少，不再启动重 SQL，直接按 timeout/degraded 处理。

## 9. SQL Timeout 分类

PostgreSQL `statement_timeout` 的 query canceled 一般对应：

```text
SQLSTATE 57014
```

必须映射：

```text
SEMANTIC_TIMEOUT
```

而不是：

```text
SEMANTIC_ERROR
```

其他 SQL 错误才是 `SEMANTIC_ERROR`。

## 10. Future Timeout 与 DB Timeout 双保险

保留上层：

```text
orTimeout(channelTimeoutMs)
```

作为最后防线。

正常关系应是：

```text
DB remaining deadline
<
Channel Future remaining deadline
<
HTTP benchmark timeout
```

目标不是绝对 0 timeout，而是：

> 超时时，昂贵底层工作也尽快结束，不继续霸占 executor。

## 11. P1：不要先调 Semantic Executor

不要第一步：


## 14. 必须新增/更新的测试

### ANN-first correctness

准备 active nearest / stale nearest / old-version nearest。

断言：

```text
最终只返回 active-valid
按向量距离顺序
bounded topK
```

### Bounded refill

第一批 ANN candidate 大量 stale：

```text
initial batch 不足 TopK
```

断言：

```text
发生 refill
budget 内存在足够 active 时最终拿足 TopK
refill rounds 有界
candidate budget 有界
```

### Refill exhausted

如果确实没有足够 active：

```text
不会无限循环
不会全表 fallback
返回已有 active candidate
标记 SEMANTIC_ANN_REFILL_EXHAUSTED
```

### Dataset isolation

另一个 dataset 的更近候选不能返回。

### Statement timeout

至少测试：

```text
SQLSTATE 57014 → SEMANTIC_TIMEOUT
```

如可用 PostgreSQL Testcontainers，再验证数据库 statement 真正被取消，worker 不继续占用数秒。

不要在生产代码加入 `pg_sleep`。

### Existing correctness

继续覆盖：

```text
stale build exclusion
sentinel recall
evidence valid
bounded results
semantic/lexical query split
timeout reporting
```
