## Combined tasks: 2.0.6 RetrievalUnit + 2.0.7 IndexBuild

> Target runtime: Java 21  
> Previous completed batch: `G2 / 2.0.3-2.0.5`  
> Migration range: `V57-V59`  
> Strategy: additive schema; V1 retrieval remains the production path

---

## 1. Goal

G2 established the source-of-truth document model:

```text
Document
  ↓
DocumentVersion
  ↓
DocumentNode
  ↓
Node Navigation
```

G3 adds the bridge between document structure and future retrieval:

```text
DocumentNode
      │
      ▼
RetrievalUnit
      │
      ├── Lexical projection
      └── Vector projection
              │
              ▼
          IndexBuild
```

Core semantics:

```text
DocumentNode  = knowledge structure
RetrievalUnit = retrieval projection
IndexBuild     = immutable physical retrieval build
```

A `DocumentNode` does not equal one vector or one BM25 document. One node may produce several retrieval units such as `PARAGRAPH`, `WINDOW`, `SECTION`, `SECTION_SUMMARY`, `TABLE`, or `TITLE_PATH` without changing the source document tree.

At the end of G3, ModelRAG has the complete V2 index data model, but online QA/search must still use the existing V1 `Chunk` path.

---

## 2. Keep three version axes separate

After G3 there are three independent version concepts.

### 2.1 Content version

```text
kb_document.active_version_id
        ↓
kb_document_version.version_no
```

Meaning: which immutable document content snapshot is current.

### 2.2 Legacy V1 index version

```text
kb_document.version
kb_document.active_index_version
        ↓
kb_chunk.version
```

Meaning: which legacy chunk index is active.

### 2.3 V2 IndexBuild

```text
kb_document.active_index_build_id
        ↓
kb_index_build.build_no
```

Meaning: which V2 retrieval projection build is active for the current content version.

Example:

```text
DocumentVersion.versionNo = 3
legacy active_index_version = 8
V2 IndexBuild.buildNo = 5
```

This is valid. Never derive one version axis from another.

---

## 3. Architectural refinement: no per-unit active flag

Do **not** add `kb_retrieval_unit.active`.

Active V2 retrieval data is derived through the document pointer:

```text
u.index_build_id = d.active_index_build_id
AND
u.document_version_id = d.active_version_id
```

Reason: if a document owns hundreds of thousands of retrieval units, switching a build must not require a mass update over all units.

Bad:

```text
activate build
↓
UPDATE 500,000 RetrievalUnits active=true
```

Target:

```text
old build state change
+
new build state change
+
one kb_document.active_index_build_id pointer update
```

Build cutover must therefore be O(1) with respect to unit count.

Update the relevant section of `docs/architecture/MODELRAG_2_REFACTOR_PLAN.md` to record this refinement only; do not rewrite unrelated sections.

## 10. RetrievalUnit consistency validation

After V59 is present, before persisting a unit verify:

```text
unit.datasetId
  == node.datasetId
  == build.datasetId

unit.documentId
  == node.documentId
  == build.documentId

unit.documentVersionId
  == node.documentVersionId
  == build.documentVersionId
```

Do not trust duplicated caller-supplied identity fields independently.

The database FKs prove existence; Java/application validation must prove aggregate consistency.

Normal indexing writes should only create units while the build is in:

```text

```

Do not allow normal unit creation into `FAILED`, `ACTIVE`, or `SUPERSEDED` builds.

```text

```

## 20. build_no must be concurrency-safe

Build numbering is per logical document:

```text
DocumentVersion 1:
  Build 1
  Build 2

DocumentVersion 2:
  Build 3
  Build 4
```

Do not perform `MAX(build_no)+1` without a lock.

Recommended transaction:

```text
SELECT kb_document row FOR UPDATE
↓
MAX(build_no)+1
↓
INSERT
```

Unique `(document_id,build_no)` is the final integrity guard.

When creating a normal production build verify:

```text
document belongs to dataset
version belongs to document
version == document.active_version_id
```

Do not silently build stale content through the standard API.

## 23. Atomic activation

This is the key G3 transaction.

Required behavior:

```text
BEGIN

lock document row

load target build

require:
  build.documentId == document.id
  build.documentVersionId == document.activeVersionId
  build.state == READY

load previous active V2 build if present

old ACTIVE
→ SUPERSEDED

target READY
→ ACTIVE

kb_document.active_index_build_id
→ target build id

COMMIT
```

If any check fails: rollback.

Activation must not mass-update:

```text
kb_retrieval_unit
kb_vector_embedding
```

and must not update Elasticsearch.

This is why activation remains O(1).
