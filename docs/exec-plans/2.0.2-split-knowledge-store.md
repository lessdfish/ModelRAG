## 2. Goal

Split the current God-style `KnowledgeStore` / `PostgresKnowledgeStore` into narrow repository contracts and JDBC implementations based on the **current V1 domain model**.

This task does NOT introduce the future ModelRAG 2.0 entities yet.

The purpose is to establish interface segregation before adding:

- `DocumentVersion`
- `DocumentNode`
- `RetrievalUnit`
- `IndexBuild`

Those belong to later tasks.

---

## 3. Current problem

The current `KnowledgeStore` owns multiple unrelated responsibilities:

```text
Dataset CRUD
Dataset routing
Dataset revision
Document CRUD
Document deletion
Document status
Legacy index version lifecycle
Chunk reads
Bounded chunk reads
Chunk writes
Chunk ID generation
```

The production implementation `PostgresKnowledgeStore` therefore owns:

```text
kb_dataset
kb_document
kb_chunk
dataset routing embeddings
index-version transitions
chunk visibility SQL
cross-table soft deletion
```

This creates a God Repository and makes later ModelRAG 2.0 domain evolution harder.

After task `2.0.1`, `RetrievalPipeline` only needs bounded chunk access, but it still injects the entire `KnowledgeStore`.

The target of `2.0.2` is:

```text
consumer
  ↓
small repository contract
  ↓
specific JDBC adapter
```

instead of:

```text
every consumer
  ↓
KnowledgeStore
  ↓
PostgresKnowledgeStore
```

---

# 5. Repository contracts

## 5.1 DatasetRepository

Move current dataset responsibilities here.

Suggested contract:

```java
public interface DatasetRepository {

    Dataset create(
            String name,
            String description,
            Integer chunkSize,
            Integer chunkOverlap);

    Dataset create(
            String name,
            String description,
            Integer chunkSize,
            Integer chunkOverlap,
            Integer topK,
            Double threshold);

    List<Dataset> findAll();

    Dataset findById(long id);

    Dataset update(
            long id,
            String name,
            String description);

    Dataset update(
            long id,
            String name,
            String description,
            Integer chunkSize,
            Integer chunkOverlap,
            Integer topK,
            Double threshold);

    void softDelete(long id);

    Dataset bumpRevision(long datasetId);

    List<Dataset> route(
            String query,
            Set<Long> allowedDatasetIds,
            int limit);

    Set<Long> findIndexedDatasetIds();
}
```

Method names may follow current project conventions.

Important:

`route()` is allowed to remain on this repository temporarily because the current dataset routing embedding is persisted in `kb_dataset`.

Do NOT build a new routing subsystem in this task.

Do not keep a default implementation that scans all chunks to discover indexed datasets.

Production and test implementations must explicitly provide bounded/index-aware behavior.

## 5.2 DocumentRepository

Suggested contract:

```java
public interface DocumentRepository {

    Document create(
            long datasetId,
            String name,
            String type,
            String hash,
            String content);

    Document create(
            long datasetId,
            String name,
            String type,
            String hash,
            String content,
            String sourceObjectKey,
            String artifactObjectKey,
            String contentHash);

    Document findById(long id);

    List<Document> findByDatasetId(long datasetId);

    void updateStatus(
            long documentId,
            String status,
            String error,
            int chunkCount);

    void softDelete(long documentId);

    void softDeleteByDatasetId(long datasetId);
}
```

The repository should own only `kb_document` persistence.

It should NOT delete `kb_chunk`.

It should NOT own vector deletion.

It should NOT emit outbox events.

Those operations belong to orchestration/application services.

---

## 5.3 ChunkRepository

This repository owns legacy `kb_chunk`.

Suggested contract:

```java
public interface ChunkRepository {

    List<Chunk> findActiveByDatasetId(long datasetId);

    List<Chunk> findActiveByIds(
            long datasetId,
            Collection<Long> ids);

    List<Chunk> findActiveByParentIds(
            long datasetId,
            Collection<Long> parentIds);

    List<Chunk> findActiveNeighbors(
            long datasetId,
            Collection<ChunkWindow> windows);

    void replaceDocumentVersion(
            long documentId,
            List<Chunk> chunks);

    void beginDocumentVersion(
            long documentId,
            long version);

    void append(
            long documentId,
            List<Chunk> chunks);

    void softDeleteByDocumentId(long documentId);

    void softDeleteByDatasetId(long datasetId);

    long nextId();
}
```

Move `ChunkWindow` out of `KnowledgeStore`.

Recommended location:

```text
com.modelrag.knowledge.repository.ChunkWindow
```

or as a nested record of `ChunkRepository`.

Prefer a top-level value type if it improves reuse and test readability.

Important:

`findActiveByDatasetId()` is a legacy/offline operation.

It may still be used by re-embedding/rebuild flows.

Document clearly:

> This method must never be used by an online retrieval hot path.

The bounded methods added in `2.0.1` remain the only methods used by query-time context expansion.

---

## 5.4 IndexVersionRepository

The current `kb_document.version / active_index_version` mechanism is a legacy index lifecycle.

Separate it from generic document CRUD now so task `2.0.7` can later replace/evolve it into `IndexBuildRepository`.

Suggested contract:

```java
public interface IndexVersionRepository {

    long begin(long documentId);

    void activate(long documentId, long version);

    Map<Long, Long> findActiveByDatasetId(long datasetId);

    Map<Long, Long> findAllActive();
}
```

Do NOT introduce `IndexBuild` in this task.

Do NOT change current version semantics.

# 7. Remove cross-table mutation from repositories

This is an important part of the split.

Current `PostgresKnowledgeStore.deleteDataset()` mutates:

```text
kb_dataset
kb_document
kb_chunk
```

Current `PostgresKnowledgeStore.deleteDocument()` mutates:

```text
kb_document
kb_chunk
```

After this task, repositories should mutate only their own aggregate/table responsibility.

Cross-table deletion must be coordinated by `DocumentDeletionService`, which already owns the transaction and outbox/vector cleanup workflow.

Target dataset deletion:

```text
DocumentDeletionService
↓
find documents
↓
append DELETE_DOCUMENT outbox events
↓
DatasetRepository.softDelete(datasetId)
↓
DocumentRepository.softDeleteByDatasetId(datasetId)
↓
ChunkRepository.softDeleteByDatasetId(datasetId)
↓
VectorStore.deleteDocument(each document)
↓
commit transaction
```

Target document deletion:

```text
DocumentDeletionService
↓
DocumentRepository.findById(documentId)
↓
validate dataset ownership
↓
append deletion outbox event
↓
DocumentRepository.softDelete(documentId)
↓
ChunkRepository.softDeleteByDocumentId(documentId)
↓
DatasetRepository.bumpRevision(datasetId)
↓
VectorStore.deleteDocument(documentId)
↓
commit transaction
```

Preserve existing transaction boundaries.

Do not move object-storage deletion into this transaction.

- remove `PostgresKnowledgeStore`
- remove `KnowledgeStore`

```text

no new code may use them
```
